# D3 · 移动端适配与草稿系统必须联动验证

**状态**：已确认（S2-3b 落地）
**日期**：2024

## 背景：定时器在后台标签页被冻结

「草稿不丢」此前的对策是两条定时线：停止输入 5 秒落盘 + 每 30 秒兜底。
两条都建立在「定时器会按时跑」这个前提上 —— 而移动端浏览器**不保证**这一点。

页面切到后台、或者被系统冻结时：

- `setTimeout` / `setInterval` 被降频到分钟级，甚至完全停止
- 页面可能被整个丢弃（bfcache 或直接杀进程），`beforeunload` 不触发
- 用户在切回来的瞬间看到的是「30 分钟前的内容」，而中间每一次自动保存都没跑

这就是一条完整的丢稿通道：**用户切出去接个电话，回来稿子回到 5 秒前。**
它不是概率问题，是「只要用户切走就会发生」。

## 决策

**落盘时机不能只依赖定时器。** 追加两个「一定会跑」的时机：

| 时机 | 为什么它可靠 |
| --- | --- |
| `visibilitychange` → hidden | 页面变隐藏时同步执行，浏览器保证在冻结前把任务跑完 |
| `pagehide` | 页面被销毁/进 bfcache 前触发。`beforeunload` 在移动端经常不触发，`pagehide` 会 |

第三条线（`freeze` 事件）能加就加，但它不是所有浏览器都支持，所以**不承担兜底责任**。

移动端兜底间隔单独缩短，理由写在代码里：移动端的「后台」比桌面端更常见、
更突然，同样的 30 秒在本机上是「无所谓」，在手机上就是「丢三句话」。

## 验收方式（Node 绿不算数）

| 场景 | 验证方式 |
| --- | --- |
| 标签页隐藏瞬间已落盘 | 真浏览器 `document.visibilityState` 模拟 → 断言隐藏后立刻读 localStorage 内容是最新的 |
| 进程被杀后恢复 | 真浏览器：写完 → 断开页面（不触发 beforeunload）→ 重开 → 断言草稿还在 |
| 多标签页 owner 在移动端的接手行为 | 真浏览器：两个上下文，断言后写的拒绝覆盖且原因如实上报 |
| 软键盘遮挡 | 移动端 viewport + 聚焦输入 → 断言目标元素仍在可视区内 |

定时器冻结、多标签页、软键盘、进程杀死恢复 —— 这四件事**只在真浏览器里成立**，
jsdom 没有渲染、没有冻结、没有进程，它给的绿灯不构成证据。

## 与 D5 的关系

快捷键表是声明面，触屏上按不出 F1。移动端必须给「快捷键的触屏替代」，
否则「说了就得有」在移动端就是空的。
