# D1 · API Key 分层存储

**状态**：已确认（S2-3b 落地）
**日期**：2024

## 决策

按可用性从高到低分三层，查找时按顺序命中第一层：

| 层 | 何时生效 | Key 存在哪 | 用户的动作 |
| --- | --- | --- | --- |
| 服务端托管 | 启动 studio 的进程环境里有 `EMEEEK_OPENAI_API_KEY` / `EMEEEK_ANTHROPIC_API_KEY`（或 `OPENAI_API_KEY` / `ANTHROPIC_API_KEY`） | 只在服务端进程内存里 | 什么都不用做 |
| 会话级 | 无服务端托管，用户在设置里填了 Key | `sessionStorage` + 内存 | 填一次，关标签页即失效 |
| 已记住 | 用户**显式勾选**「记住这个 Key」 | `localStorage` | 每次打开自动带上 |

## 为什么默认不是「记住」

API Key 是长期凭证，泄露一次要去后台吊销。而「记住我」是用户做的一个有意识的决定 ——
默认替用户勾上，等于替用户决定了「以后别人用这台机器也能花我的额度」。
安全默认值的成本是「多勾一次」，收益是「默认状态下的暴露面为零」。

## 为什么服务端那层优先

因为它是唯一「Key 不进浏览器」的形态。浏览器直连 provider 意味着 Key 必须到达页面，
于是它同时存在于 DevTools 网络面板、每一个装了的浏览器扩展、
以及「不小心把 sessionStorage 导出来贴进 Issue」的风险里。
这些都不是「密钥管理做得好不好」的问题，是它根本不该来。

服务端代理的兑现点有三条，缺一条这个分层就等于没做：

1. `/__studio/ai/status` 只说「有没有配置」，一个字符的 Key 都不回
2. `/__studio/ai/run` 由服务端带 Key 转发，浏览器只拿到结果
3. **回给浏览器的错误信息先消毒** —— 上游 401 的响应体里经常把请求头回显回来

## 为什么不接受配置文件里的 Key

配置文件进 git。「把 Key 提交上去」是这类事故里最常见的一种。
只认环境变量（或显式传入，测试用）。

## 输出面扫描

存得再严，一条把 Key 拼进错误消息的日志就全废了。所以 `redact` / `scanForSecrets`
覆盖所有会产出文本的路径：错误信息、日志、导出、URL 查询串、认证头。

`scanForSecrets` 同时被**生产代码**（代理返回前的兜底）与**测试**（断言）使用 ——
一份实现，不存在「测试扫的规则与运行时扫的不一样」。

## 附：这条决策的负向证据

`scripts/e2e/negative-check.sh` 会逐条削弱这些防线并确认测试变红：

- 让「记住」变成默认 → `keyring.test.js` 必须红
- 让 `redact` 变成恒等变换 → 必须红
- 让状态接口回 `apiKey` → 必须红
