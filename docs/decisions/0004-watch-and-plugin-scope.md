# D4 · 文件监听与插件访问范围收敛

**状态**：已确认（S2-3b 落地）
**日期**：2024

## 决策

### 一条校验，多个入口

`resolveProjectFile` 是唯一的路径守门人，三条防线：

1. 拒绝 NUL 字节（会在 fs 层截断路径）
2. 解析后必须仍在内容目录内（挡 `../` 与绝对路径）
3. **真实路径也要在内容目录内**（挡符号链接）

S2-3a 已经在 HTTP 那条入口装好了它。S2-3b 新增的两个入口必须走**同一个函数**，
不允许「再写一遍差不多的判断」：

| 入口 | 校验 |
| --- | --- |
| HTTP `/__studio/file` | `resolveProjectFile` |
| 文件监听（fs.watch / 轮询） | `resolveProjectFile`（事件路径先归一再判） |
| 插件读取项目文件 | `resolveProjectFile` |

为什么要强调「同一个函数」：多一份实现就多一次「这个入口忘了看 realpath」的机会，
而 S2-3a 那个符号链接的洞正是被测试抓出来的 —— 它当时也「看起来没问题」。

### 监听范围 = 内容目录

不监听项目根、不监听家目录。原因有两个：

- **安全**：监听整个项目根意味着 `.env`、`node_modules`、`.git` 的变动都会进管线
- **可用**：编辑器里一次 `git status` 就能造出成百上千个事件，dev server 直接被打瘫

监听器异常必须隔离：某个路径 watch 失败（权限、文件被删、平台限制）只记一条警告，
dev server 继续跑。**监听挂了不是致命的，拖垮 dev server 才是。**

### 插件不提供任何读取 Key 的接口

这一条是**立规**，不是实现细节：

- 插件 API 里没有、也不会有 `getApiKey()` / `config.ai.apiKey`
- 传给插件的 `config` 经过剔除：`ai` 字段里的所有凭证在进入插件前就没了
- 插件的文件访问过 `resolveProjectFile`，代码路径限制在项目内

理由：插件生态的安全模型是「装插件 = 信任它的全部权限」。
既然无法审核每一个插件，那就不要在 API 层给它一个本不该有的能力。
这把钥匙不给出去，比给了之后写文档劝阻有效得多。

### 插件能力声明（manifest）

先立规则再写 API：

```javascript
export default {
  name: 'reading-stats',
  capabilities: ['content:read'],   // 未声明即拒绝
  hooks: { onContentLoad(ctx) { /* … */ } },
};
```

未声明能力的插件调用对应 API → 拒绝并记录「哪个插件、缺哪个能力」。
超时与异常隔离：任何插件 bug 都不得影响草稿保存主链路。**草稿 > 插件。**

## 负向证据

- 越权插件被拒（测试）
- 监听器收到目录外路径被拒（测试，含 symlink 场景）
- 削弱 `resolveProjectFile` 的 realpath 判定 → 测试必须红
