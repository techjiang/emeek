# 0008 — 分析层：零追踪与构建期推断

- 日期：2026-03-02
- 阶段：P3-4b-rest（A 分析集成 + B 统计页）
- 状态：已采纳

## 背景

博客引擎默认带不带分析、带什么样的分析，是一个**价值观问题**，不是功能问题。
市面上多数博客主题/框架的做法是：默认塞一个 Google Analytics，
想关掉要自己去找开关、还要自己删掉一段已经进产物的脚本。

Emeek 的目标用户是「在意自己站点上跑了什么」的人。对他们来说，
**默认开追踪就是背叛** —— 他们选 Emeek 的理由之一就是它干净。

同时有一个现实约束：Emeek 的基因是「Issues 即 CMS」。
内容本来就在 GitHub 上，评论、reaction、发布时间、标签全都是 GitHub 的一等对象。
这意味着**一类统计根本不需要运行时**。

## 决定

### 1. 默认零追踪：`analytics.enabled: false` 时产物里零脚本

不是「加载了但不发送」，是**根本不生成**。

实现点在 `analytics/providers.js` 的 `buildAnalyticsScripts()`：

```js
if (analytics.enabled !== true) return { head: '', footer: '', provider: null, origin: null };
```

模板层无条件输出 `{{{ analyticsHead }}}` / `{{{ analyticsFooter }}}`，
关掉时它们就是空字符串。所以「关掉」与「不配这个功能」的产物是**逐字节相同**的
（有测试钉住这一点）。

### 2. 内置分析全部在构建期算

`analytics/builtin.js` 是一组纯函数：`posts` 进，数据出。
它要的东西全在内容里：标题、日期、标签、字数、Issues 互动计数。

这样做的收益不只是「省一个服务」：

- 零运行时依赖 → 静态托管上也能有统计
- 纯函数 → 可以直接断言，不需要跑浏览器
- 不采集 → 没有合规问题

### 3. 区分 `null` 与 `0`

这是这一层最重要的一条纪律。

`null` = 没有这个数据源。`0` = 有数据源，值是 0。

- 没有 Issues 数据的 `local` 源 → `comments: null`（不是 0）
- 构建期永远造不出 PV → `pv: null`（不是 0）

页面上 `null` 渲染成 `—` 并标注「无数据源」，`0` 渲染成 `0`。

如果两者都渲染成 0，读者会得出「这个站没人看」的结论 —— 而真相是
「我们没打算知道」。这两件事在展示上必须可区分。

### 4. 图表在数据为空时整块不渲染

同样不许画一个全 0 的图。空数据时 `charts.js` 的每个函数返回**空字符串**，
页面据此跳过整个 `<section>`。

一个全 0 的柱状图看起来像「有数据，只是都是 0」；
一块消失的区块看起来像「这里没有这一项」—— 后者才是真相。

### 5. 统计页与「要不要追踪」是两个开关

`analytics.statsPage.enabled` 与 `analytics.enabled` 独立。

- 想要统计页但不想开任何分析 → `statsPage.enabled: true, enabled: false`
- 想开分析但不想要公开页面 → `enabled: true, statsPage.enabled: false`

把它们绑在一起，两种人都拿不到自己想要的。

### 6. 统计页纯 HTML + SVG，零 JavaScript

图表在构建期把坐标算完，产出内联 SVG。

- 不需要图表库 → 不引第三方 JS（这与「零追踪」是同一条线的两端）
- 对爬虫 / 阅读器 / 打印 / 禁用 JS 的浏览器都可读
- `<title>` / `<desc>` 里有真实数值，屏幕阅读器能念出来

### 7. 唯一会发数据的代码，自我约束硬编码

`analytics/probe.js` 是「内置 PV」，需要用户自托管端点。它：

- 不读 Cookie / localStorage
- 不发明文 IP、不发明文 UA（两者各取 FNV-1a 哈希做粗去重）
- 不发 referer / 屏幕尺寸 / 语言 / 时区
- 只发 pathname（不带 query —— 那里面有 token）
- 失败静默、不阻塞首屏、优先 `sendBeacon`

这些**不是配置项**，是测试钉死的断言。想改就得删测试。

## 放弃的方案

### 引入 Google Analytics 作为选项

不是「不好」，是**与产品定位冲突**。一个以「干净」为卖点的引擎，
把最不干净的那家放进 provider 列表，会让「零追踪」这句话变成「默认零追踪，但你随时可以破戒」——
而大部分人不会主动破戒，会**顺手**配上。列表本身就是引导。

### 用 CDN 加载图表库，统计页才好看

统计页是可选的二级页面，为了它给全站引入一个 JS 依赖，与 `perf` 那一整章的努力矛盾。
而且 `chart.js` / `d3` 之类的库会把「零 JS」这个可验证的硬指标变成「少 JS」这种软说法。

### 统计页做成客户端渲染（fetch 一个 stats.json 再画）

- 多一次请求，且这次请求在首屏关键路径之外，会闪
- 无 JS 时页面是空的 —— 而「统计页对爬虫可读」是有价值的
- 数据在构建期就有，序列化成 JSON 再让客户端算一遍，纯粹是绕远路

### 把探针的 `u` 落盘（方便做「回访率」）

落盘之后那串哈希就成了一个可关联的访客 ID，
探针这一侧的克制（不存 Cookie、只发哈希）就白费了。
**拿不到回访率是这个设计的代价，不是它的 bug。**

## 后果

### 好的

- 「零追踪」是一个可以被测试验证的事实，不是一句宣传语
- 构建期推断让「静态托管 + 有统计」这个组合成立
- 统计页零 JS → Lighthouse 不扣分，与其它页面同一条基线
- `custom` provider 之外，没有任何路径能往第三方发数据

### 代价

- 得不到 PV（除非自托管探针），得不到 referer，**永远**得不到。
  这是设计的一部分，文档里明说。
- 用户想要「跟 GA 一样全的报表」时，Emeek 给不了。这是有意的取舍。
- `custom` provider 是一个口子：它能往任意域发数据。
  我们选择保留它（有人确实需要），但让文档与 doctor 反复警告。

### 怎么保证不退化

- 15 条负向验证：削弱「零追踪」「不读 Cookie」「不发 query」
  「空数据不画图」「无数据源不显示 0」「图表零 JS」「标签转义」
  等任一条，测试必须变红
- `stats.mjs` e2e：真实构建 + 真 Chromium，断言统计页零 `<script src>`、
  无 canvas、有 SVG 图表、无数据源的区块真的不在了
