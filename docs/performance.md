# 性能基线

这份数字不是目标，是**实测结果**，由 `scripts/lighthouse.mjs` 在
Chromium headless 下跑出来，可随时复现。

## 产物体积

| 指标 | 实测 | Phase 1 目标 |
| --- | --- | --- |
| 单个 HTML（含内联 CSS/JS） | 17–23 KB | < 50 KB |
| 构建产出的 JS 文件 | 0 个 | < 30 KB (gzip) |
| 外部网络请求 | 0 个 | — |
| 3 篇文章的完整站点 | 206 KB / 16 个文件 | — |

**没有独立的 JS 文件**：主题脚本内联在 HTML 里，约 6 KB 未压缩。它负责主题切换、
阅读进度、目录高亮、代码复制与搜索 —— 全部延迟到 `</body>` 前，TBT 仍为 0–20 ms。

## 这些数字是怎么来的

不是靠事后优化，是设计约束倒推出来的：

1. **零外部请求** —— 没有字体、没有 CDN、没有分析脚本。用系统字体栈，
   代价是放弃品牌字体，换来的是首屏没有 FOUT/FOIT。
2. **关键 CSS 内联** —— 主题 CSS 约 9 KB，一个 RTT 的收益大于缓存收益。
   超过 24 KB 时自动退回外链（见 `output.js`）。
3. **高亮在构建期完成** —— 浏览器不下载语法定义，`<span class="tok-*">` 直接躺在 HTML 里。
4. **脚本默认不阻塞** —— 交互逻辑（主题切换、阅读进度、搜索）全部延迟到 `</body>` 前，
   且在 `IntersectionObserver` / 事件回调里才真正干活。

## 满分不是一次到手的

第一轮实测时，Best Practices 96、Accessibility 95，扣分项都是真实问题：

- **缺 favicon** → 触发一次 404 请求，控制台报错
- **正文链接只靠颜色区分** → 色觉障碍用户无法识别，改为下划线
- **代码块语言标签与注释对比度不足** → 浅色底上只有 3.6:1，加深一档到 4.5:1
- **任务列表复选框没有可访问名称** → 补 `aria-label`

这些都不是「为了分数」的调整，是本来就应该修的问题。

## 复现方式


脚本会构建 `examples/minimal`、起一个本地静态服务器、逐页跑 Lighthouse，

## Studio 客户端体积（S2-3b 复测）

门禁 600KB，S2-3b 结束时 **350KB 入口 + 38 个按需 chunk（共 1677KB）**。

| 阶段 | 入口 |
| --- | --- |
| S2-3a | 311KB |
| S2-3b | **350KB**（+39KB / +12.5%） |

涨幅构成，逐项都有理由：

| 新增 | 大约 | 为什么必须在首屏 |
| --- | --- | --- |
| URL / HTML 消毒（sanitize-url + sanitize-html） | ~6KB | 预览渲染每次输入都会走它 —— 懒加载等于「预览第一次渲染还是能注入」 |
| Key 状态机 + 输出面消毒（keyring） | ~7KB | 面板一打开就要显示状态，而 `redact` 是日志出口的一部分 |
| 快捷键声明表 + F1 渲染（shortcuts） | ~9KB | F1 表是声明面，按住就能弹是它唯一的用法 |
| 落盘时机 + 移动端布局（drafts/client 增量） | ~6KB | `visibilitychange` 必须在页面隐藏的那一瞬就绪，不能等懒加载 |
| 热更新同步（sync） | ~5KB | SSE 要尽早连上，否则开页面头几秒的磁盘改动会漏 |
| 其余（diff） | ~6KB | |

**没有选「懒加载它们换首屏」**：这五项各自的触发时机都在用户第一次交互之前
或之上的瞬间（隐藏、渲染、连通道），懒加载会把它们的生效时间推迟到
「已经被需要之后」。39KB 换的是「这些防线从第一帧起就是活的」。

chunk 数（38）与总大小（1677KB）不变 —— 说明语言语法仍然是按需的，
这次涨的全在入口。

## 性能自检（check-perf.mjs）

`node scripts/check-perf.mjs` 盯的是**具体的事实**，每条能单独失败、单独定位。

为什么在 Lighthouse 之外还需要这个：Lighthouse 是端到端黑盒。
少了一条 preload、首屏图被懒加载了、某个 CSS 悄悄超过内联阈值、
PWA 预缓存把整站都塞进去了 —— 这些在 Lighthouse 上的表现只是
「分数从 100 掉到 96」，**仍在阈值之上**，门禁不会红，但站点已经变慢了。

| 类别 | 盯什么 |
| --- | --- |
| 预算 | 单页 gzip 体积、内联 CSS 体积、产物总字节 |
| CSS 落位 | 主题 CSS 是否内联、变量覆盖块顺序、外链样式表是否真的存在 |
| 图片 | 首屏图 eager+fetchpriority、其余 lazy、alt 非空、srcset 诚实 |
| 资源提示 | 预取的地址是站内的、真的存在、有条数上限、不做无效 preconnect |
| PWA | manifest 结构、图标是否存在、SW 缓存名带指纹、预缓存不是整站 |

**按 gzip 而不是原始字节算预算**：原始 HTML 体积几乎完全由
「内联了多少 CSS / 索引」决定，而这些在传输时 gzip 掉 3~4 倍。
按原始字节卡阈值，最后一定会变成「把阈值调大以放过它」——
因为被卡住的从来不是用户真正下载的字节数。

三个站点分别跑，因为它们的检查对象不同：

```bash
node scripts/check-perf.mjs                              # examples/minimal（性能基线）
node scripts/check-perf.mjs --site examples/themes-demo  # 有图片的站点（图片规则才有对象）
node scripts/check-perf.mjs --pwa                        # 开了 PWA 的站点（PWA 规则才有对象）
pnpm check:perf:all                                      # 三个都跑
```

### 为什么要三个站点

这是这一层最容易自欺的地方：**检查写在只有空转对象的站点上**。

- `examples/minimal` 里一张 `<img>` 都没有 —— 图片相关的四条规则
  在这个站点上永远绿，无论实现多烂。
- `pwa.enabled` 默认 false —— 在没开 PWA 的站点上，整套 PWA 检查
  只会输出一句「未启用」。
- 预缓存上限（5 篇）在只有 3 篇的站点上永远触发不了 ——
  「全站预缓存」的错误做法与正确做法产出完全一样。

所以 `examples/themes-demo` 里加了一篇带四张图的文章
（首屏图 / 正文图 / 无 alt 图 / 数字文件名各一张），
`examples/pwa-demo` 是 12 篇文章 + 开启 PWA 的独立示例站。

### 负向验证

```bash
bash scripts/e2e/perf-negative.sh
```

13 条防线逐条削弱，`check-perf` 必须变红。这一步抓出过三个真实问题：

1. **「页面里有 `<style>`」永远为真** —— 变量覆盖块本身也是 `<style>`，
   所以「主题 CSS 完全没内联」时这条检查仍然是绿的。它看起来在守
   「关键 CSS 落位」，实际只守住了「有个 style 标签」。
   现在按「有规则块且有选择器」区分主题样式表与变量块。
2. **「图有 alt 属性」永远为真** —— 空 alt 也是 alt。
   空的 `alt=""` 让图片对屏幕阅读器与图片搜索**完全消失**，
   而只判断「有没有 alt 属性」会把这个空串当成「作者写过了」。
3. **豁免项会让聚合失效** —— 404 页的 SEO 分被豁免成字符串 `'—(豁免)'` 后，
   `Math.min(...)` 得到 NaN，于是 `worst < 阈值` 永远为 false，
   **整个门禁静默失效**。现在先过滤出数值项，拿到空列表直接报错。

### 一处豁免，以及它的对价

`lighthouse.mjs` 里 404 页的 SEO 分被豁免。理由写在脚本顶部：

Lighthouse 的 `is-crawlable` 对**带 noindex 的页面**记 0 分，于是整页 SEO
从 100 掉到 66。而 404 页恰恰**应该**带 noindex —— 一个「页面不存在」的页面
被收录，是纯粹的错误结果。这与 P3-3a 在搜索页上做的是同一条判断。

豁免的**对价**是：`check-seo.mjs` 直接断言 404 页带 noindex 且不在 sitemap 里，
`perf-negative.sh` 之外还有一条削弱它会让 SEO 自检变红。
不是把阈值调低（那会连带放过真回归），是把这一项换成更准确的形式守住。

这一点之前是断的：P3-3a 给 404 加了 noindex（正确），
但基线脚本没跟着更新，于是「SEO 66」在门禁里一直是红的而没人修 ——
**一条长期红着的门禁等于没有门禁**。

## PWA 性能

PWA 默认关（理由见 [pwa.md](pwa.md)）。打开时对性能的影响：

| 项 | 影响 |
| --- | --- |
| SW 注册脚本 | ~0.5KB 内联，且在 `load` 之后才跑，不进首屏关键路径 |
| manifest | 1 个额外请求，浏览器在空闲时取 |
| 首屏 | **无影响** —— 注册在首屏之后，预缓存在 install 阶段 |
| 次次访问 | 静态资源走缓存，省掉网络往返 |
| 断网 | 导航回落缓存，离线页保证有东西可看 |

`precachePosts` 默认 5：预缓存发生在首屏之后，全站预缓存等于
给每个首次访客偷偷加一次全站下载。
