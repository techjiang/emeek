# 中文字典

`zh-words.txt.gz` —— 128,926 个中文词条（2~4 字），用于本地分词。

## 为什么要内置一份词典

摘要器要算 TF-IDF，可读性要算词汇丰富度，SEO 要提关键词 —— 这三件事都
需要「知道什么是词」。英文有空格，中文没有。

我们试过零词典的互信息切分：**不可行。** 无词典分词在短文本上会切出
`客引`（博客引擎）、`擎基`、`让写和` 这类跨词碎片，直接污染关键词表。
用户看到的关键词会是一堆乱码，比不分词还差。

## 来源与许可

词条从 [segmentit](https://github.com/linonetwo/segmentit) 的词典中筛选而来，
该项目为 **MIT 许可**，允许再分发。我们再筛选为「2~4 字 + 内容词（非虚词）
或出现频率 ≥ 200」，保留 12.9 万条。代码部分未使用 —— 只有词表数据。

## 格式

纯文本，一行一词，**front-coded**（前缀压缩）后 gzip：

- 每行首字节是个字符码，表示「与上一行共享的前缀长度」
- 其余部分是这一行的新后缀

```
原词表（按字典序）        编码后
博客                       \x02博客
博客引擎                   \x02引擎
静态                       \x00静态
```

因为词表按字典序排列，相邻词共享大量前缀，front-coding 把 448KB 压到 409KB，
gzip 后仍是同一量级。压缩格式本身是 gzip，所以 Node 用 `zlib`、
浏览器用 `DecompressionStream('gzip')` 都能直接解，无需额外依赖。

## 加载策略

**惰性加载，不阻塞首屏。** 这个文件只在用户真的触发需要分词的功能
（快速摘要 / 关键词提取）时才读取。分词不可用时，摘要器退回字级统计 ——
质量差一些，但功能不中断。

加载入口见 `../segmenter.js`。

## 更新词表

词表是生成物，不是手写的。重新生成需要 seed 端的 segmentit 词典，
属于离线步骤，不在构建流水线里。替换时保持 front-coded + gzip 格式即可。
